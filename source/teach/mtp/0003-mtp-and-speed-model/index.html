MTP 如何成为 proposer

本节把训练目标、候选生成和正确性验证分开，再用一个可计算的速度模型回答：为什么“预测更多 token”不等于“推理一定更快”。

先预测

一个模型训练时加入 4-token MTP loss。推理时直接一次输出 4 个 head 的 argmax，不做 target verification。它是否自动等价于原模型逐 token 解码？

1. 三层概念不要折叠

MTP objective

训练时让同一位置的表示预测多个未来 token，增加监督密度，并可能促使表示提前规划。

Proposer / draft

推理时低成本产生一段候选及相应 qᵢ。它可以来自 MTP heads，也可以是独立小模型、EAGLE、n-gram 等。

Speculative decoder

让 target 一次评分候选，并执行 accept/correct。它保证 greedy 一致性或 stochastic 分布一致性。

一句话关系

MTP 可以让 proposer 又便宜又接近 target，从而提高接受率；但 MTP 本身不是 speculative decoding，也不负责无偏性证明。

2. 通用的并行-head MTP

Gloeckle et al. 的结构用共享 Transformer trunk 产生上下文表示 z≤t，再用 n 个独立输出 head 分别预测 xₜ₊₁ … xₜ₊ₙ：

Ln = − Σt Σi=1..n log Pθ(xt+i | z≤t)
Shared trunk读取真实 prefix，生成同一个上下文表示。
Head +1预测下一个 token。
Head +2从同一 prefix 表示预测第二个未来 token。
Head +3/+4继续预测更远位置。

这些 future heads 的预测共享已知 prefix，但后面的 head 并没有条件化在前面 head 实际生成的 token 上。因此，单独看各位置都可能很准，拼起来却未必是一条连贯的自回归路径。用于推理时，需要 blockwise verification 或 tree candidates 来筛出有效前缀。

该论文把额外 heads 用于 greedy self-speculative decoding：7B、4-token prediction model 在 code 上平均每次 forward 取回 3.50 个 token，报告相对速度 3.05×；这说明 MTP 能形成高质量 proposal，但数值是特定模型、数据和实现的实测结果，不是结构保证。

3. DeepSeek-V3 的顺序 MTP modules

DeepSeek-V3 没有采用“所有 future heads 只看同一个 trunk state”的并行结构，而是串接 D 个 MTP modules。第 k 个 module：

  1. 取得上一深度的表示 hᵢᵏ⁻¹；
  2. 拼接第 i+k 个 token 的 embedding；训练时它是真实 token，推理 draft 时对应前一深度产生的 token；
  3. 经过线性投影和一个 Transformer block，得到 hᵢᵏ；
  4. 用与主模型共享的 output head 预测再下一个 token。
h′ik = Mk[RMSNorm(hik−1); RMSNorm(Emb(ti+k))]
hk = TRMk(h′k),　Pik+1 = OutHead(hik)

这保留了完整 causal chain：更深的预测显式接收前一个未来 token，而不是从同一个静态 prefix 独立猜更远的位置。DeepSeek-V3 report 也明确说，MTP 的首要目的仍是改善主模型训练；推理时可以丢弃 modules，也可以把它们改作 speculative decoding。

5. 理论 tokens/iteration

假设每个 draft token 的接受事件独立同分布，平均接受率为 α。第 1 个 token 一定产出；要产出第 2 个，需要第 1 个 draft 被接受；要产出第 k+1 个，需要前 k 个都被接受。因此：

E[tokens / iteration] = 1 + α + α² + … + αγ = (1−αγ+1)/(1−α)

当 α=1 时取极限，等于 γ+1。当 γ→∞ 时上界是 1/(1−α)：若 α=0.8，即使无限加长 draft，理想平均产出也只趋近 5。

6. 理想速度模型

令一次 target decode step 耗时为 T，一次 draft step 耗时为 cT。理想化假设 target 对 γ+1 个位置的并行验证仍耗时约 T，一轮成本就是 (1+γc)T：

speedup = (1−αγ+1) / ((1−α)(1+γc))

7. 现实中为什么低于公式

把 target verification 相对单 token decode 的成本记为 v(γ,B,L)，再加入调度、采样和状态管理开销 o，更诚实的估算是：

practical speedup ≈ E[tokens/iteration] / (v(γ,B,L) + γc + o)
变量为什么会恶化你应测什么
v候选越长，attention、activation、logits 和 kernel 工作量越大；大 batch 时 target 本来就 compute-boundverify forward latency / baseline decode latency
c独立 draft model 太大、跨设备通信，或 MTP modules 太深每 proposal token 的端到端成本，不只看参数量
α高温度、开放域难 token、draft/target tokenizer 或 sampling processor 不一致按位置的 acceptance curve，而不只看整体平均值
o动态 batch 重排、概率张量搬运、rejection sampling、KV truncate/recompute非模型 kernel、CPU 调度和同步时间
吞吐与延迟不是同一结论

投机解码最自然地改善低 batch、memory-bound decode 的单请求延迟。高并发时，baseline 已能用 batch 填满 GPU；额外 draft 与 verification FLOPs 可能降低总吞吐。任何“x 倍加速”都必须同时给出 batch、序列长度、采样参数、硬件和指标定义。

8. 读论文与源码时的判断顺序

  1. q 从哪里来？ 独立模型、并行 heads、顺序 modules、隐藏层退出，还是检索/n-gram？
  2. 候选是否构成真实 causal chain？ 若不是，是否用 tree attention 或 blockwise verification？
  3. 验证保存什么语义？ greedy 完全一致，还是 stochastic 分布严格一致，或只是近似阈值？
  4. qᵢ 是否真的是产生 yᵢ 时的分布？ sampling processor、temperature 和概率张量是否对应？
  5. 首拒后的状态如何处理？ token、position、KV block 和 RNG 状态是否只提交有效前缀？
  6. 速度报告由谁贡献？ 接受率、draft 成本、verify 成本还是 batching 策略？
收尾检索

一个 MTP proposer 的 token acceptance 达到 90%，是否足以断言系统一定加速？

本节压缩

  • MTP 是训练目标/候选结构；speculative decoder 才执行 target verification 与分布修正。
  • 通用 MTP heads 可从同一 prefix 并行预测多个未来位置；DeepSeek-V3 用顺序 modules 保留 token 间因果链。
  • 理想每轮 token 数是 Σₖ₌₀ᵞ αᵏ，收益随 draft 长度递减。
  • 真实速度由 acceptance、draft cost、verification inflation、batching 和状态管理共同决定。

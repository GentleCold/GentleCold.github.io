先回忆

顺序 MTP 已经提出 y₁=吃。它预测 y₂ 时能看到哪个上下文？

这轮只回答一个问题

当前真实前缀是 我 喜欢。一轮结束后，哪些 token 会成为真实输出，哪些 KV 可以继续使用？不要先算；点击“下一步”跟着状态变化走一遍。

起点：只有真实前缀

我 喜欢

此时 token 状态和 target KV 都只覆盖 我 喜欢。MTP proposer 接下来会提出三个候选。

步骤 1：MTP 生成候选块

我 喜欢 吃 y₁ 苹果 y₂ 。 y₃

顺序 MTP 使用的候选概率是：

  • q₁(吃)=0.60，条件是 我 喜欢；
  • q₂(苹果)=0.50，条件是 我 喜欢 吃；
  • q₃(。)=0.70，条件是 我 喜欢 吃 苹果。

如果 proposer 是并行 heads，后两个 head 不会看到前面的候选；但候选块交给 target 后，下面的验证流程相同。

步骤 2：target 一次评分候选路径

1吃0.600.480.800.30

target 可以沿候选路径一次算出这些 pᵢ。但是 sampler 必须从左到右检查，因为第一个拒绝会改变后面位置的条件前缀。

步骤 3：接受第一个候选

我 喜欢 吃 接受 苹果 。
u₁ = 0.30 < min(1, 0.48 / 0.60) = 0.80

吃 进入 accepted prefix。现在才能继续检查第二个候选。

步骤 4：拒绝第二个候选并修正

u₂ = 0.70 > min(1, 0.20 / 0.50) = 0.40

苹果 被拒绝。这个位置的完整分布如下：

tokentarget p₂draft q₂缺口 (p₂-q₂)+修正分布
苹果0.200.5000
香蕉0.500.200.301
梨0.300.3000

因此修正 token 必然是 香蕉。拒绝的 苹果 不可能在 residual 中再次被采到。

步骤 5：首拒后，旧后缀全部作废

我 喜欢 吃 香蕉 修正 苹果 。

y₃=。 原来是根据 我 喜欢 吃 苹果 提出的。现在真实前缀变成了 我 喜欢 吃 香蕉，所以旧的 q₃ 和 p₃ 都不再对应当前条件，不能继续验证。

终点：分别看 token 状态与 KV 状态

逻辑 token

我 喜欢 吃 香蕉

吃 是 accepted token，香蕉 是 correction token。

可复用 target KV

我 喜欢 吃

verification 已计算并确认了 吃 的 KV；候选 苹果、。 的 KV 必须丢弃。

为什么香蕉的 KV 还没有？

香蕉 是从 p₂ 的 residual 采出来的，但它没有作为 verification 的输入 token。普通实现要在下一步处理它，或通过专门的融合/重算路径补出它的 KV。

把整轮压成四条规则

  1. MTP 先产生候选块和实际使用的 q₁…qγ。
  2. target 沿候选路径一次得到 p₁…pγ+1，sampler 再从左到右验收。
  3. 首次拒绝时，从该位置的 residual 采 correction，并立即停止本轮验证。
  4. 逻辑 token 提交 accepted prefix 与 correction；KV 只保留确实对应真实路径的部分。
收尾检查

y₂ 被拒绝并修正后，是否还能继续验证旧的 y₃？
